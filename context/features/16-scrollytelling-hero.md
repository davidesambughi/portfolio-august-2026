## Architecture, rules and constraints

- **Motion library: `motion`** (npm package `motion`, imported from `motion/react`; version `13.2.0` — confirmed current via `npm view motion version` this session, not assumed. `framer-motion` is the legacy package name, no longer the actively developed one — not installed, do not import from it). Installed this unit — see `architecture_context.md`, "Deciso", 2026-09-13 entry. This is a deliberate, documented exception to the unit 13b decision ("no external motion library" for the rest of the site) — that decision stands unchanged for every already-built section; it does not apply to this new scrollytelling homepage, which needs continuous scroll-scrubbed values (`p` 0→1 per chapter), not one-shot reveals.
- **Verify current `motion` docs before implementing** (official docs at motion.dev, package name `motion`), per `AGENTS.md`'s doc-first rule — the API surface (`useScroll`, `useTransform`, `useMotionValueEvent`) is stable but must be checked against the installed `13.2.0`, not assumed from training data.
- **SEO**: all copy stays in the DOM as real text at all times. Animate only `transform`, `opacity`, and `color`. Never mount/unmount text based on scroll position, never `display:none` indexable copy.
- **`prefers-reduced-motion`**: reduced-motion users get the static mobile-style layout (see Design), not the pinned/animated one with effects merely disabled — per the handoff's explicit instruction ("saltare i pin, rendere i capitoli come sezioni statiche impilate").
- **Progressive enhancement for the word-reveal effect**: the paragraph's words render at full ("lit") color in the server-rendered HTML. The dimming/reveal effect is applied only once client JS has mounted. This is a different concern from `prefers-reduced-motion` (it also covers JS failing to load) — see Implementation step 4.
- **i18n**: no hardcoded copy in components. Reuses existing `messages/en.json` / `messages/it.json` keys (`hero.name`, `hero.badge`, `hero.role`, `hero.body`, `hero.ctaProjects`, `hero.ctaContact` — all six confirmed present in both locale files this session) via `next-intl`. One new namespace, `chrome`, is added for the two small pieces of new UI copy the handoff introduces (brand tagline, scroll hint) — see Implementation step 1.
- **Content as data, not markup**: `hero.body`'s word-split for the reveal effect must tolerate the string changing later (±30% length) — split at render time on whitespace, not hardcoded per-word markup.
- **Scope of this unit is Hero + the shared chrome only.** Every other homepage section (Projects, Education, Experience, Skills, About, Contacts/Footer) is untouched and keeps its current light, non-pinned design below the new Hero for now. This is an expected, temporary visual mismatch — each remaining chapter gets converted in its own unit, per the handoff's suggested build order.
- **Nav decision (confirmed with user this session)**: the current sticky pill `Nav` (section links, mobile hamburger, language switcher) is removed from this position and replaced by the handoff's minimal fixed brand mark (name + tagline, `pointer-events: none` on the row itself). **Language switching stays** — it's relocated into this same row, top-right next to the tagline (confirmed with user), not dropped. The existing `components/language-switcher.tsx` is reused, not rebuilt.
- Jump-to-section navigation (the old pill's 6 links) has **no replacement yet** — still an open question, not solved in this unit. Log it in `progress_tracker.md`'s Open Questions once this unit is built (per the project's timing rule — not before).
- Do not delete `components/nav.tsx` — it stops being rendered on the homepage, but its scroll-spy/hamburger logic may inform how jump-to-section navigation gets reintroduced once that open question is resolved.
- Existing design tokens only — every color used below already exists in `app/globals.css` (`--color-accent-teal`, `--color-on-accent`, `--color-heading`) or is pure black/white, matching the handoff's "no new colors invented" note. No new tokens needed for this unit.
- **Mandatory invariant — `transform` breaks `position: sticky` on any descendant.** A `transform` on _any ancestor_ of a `sticky` element changes that ancestor into its containing block, which breaks the sticky behavior (already documented in `ui_context.md`, the About collage case). The Hero chapter's sticky panel is the pinning mechanism this whole unit depends on, so: `transform` (including via `useTransform`/`motion.div`) is applied only to elements _inside_ the sticky panel (the background image, the text, individual word spans) — never to the `<section>` track itself, never to the `sticky` div, and never to any wrapper placed above either of them in `hero-chapter.tsx` or `page.tsx`. Every one of the other six chapters will copy this file's structure — get this rule explicit and correct here, since it propagates.
- **Mandatory invariant — one markup, CSS-only presentation split. Applies to the shared chrome as much as to each chapter.** The Hero chapter is written **once** in the DOM: one `<h1>`, one paragraph, one set of CTA links. There is no separate "pinned version" and "static version" of the markup. Every presentational difference between the motion-safe/desktop rendering and the static/narrow/reduced-motion rendering — pin on/off, track height, typographic scale, image at 70% vs 110% width, gradient, which CTA(s) show — is expressed in CSS only (`min-[820px]:` and the mount/preference gate described below), not by rendering two trees. The same rule governs `scroll-chrome.tsx`: it is **one** nav row, **one** `hero.name` span, **one** `chrome.tagline` span, **one** small CTA pill, and **one** `<LanguageSwitcher />` instance — not a desktop copy and a mobile copy each with their own. `fixed` vs `sticky` positioning, transparent vs solid-black background, and which elements are visible (progress bar and small CTA pill only above `820px`) are CSS variants of that single row. Two mounted `<LanguageSwitcher />` instances would mean two live interactive dropdowns in the DOM simultaneously (one merely hidden by CSS) — both reachable by keyboard tab order and both wired to the same routing state — which is exactly the kind of duplication this invariant exists to prevent.
  The one decision CSS cannot make is whether to attach `useScroll` at all (for the Hero chapter) or the scroll-tick color-switching logic (for the chrome). See the separate **mount/reduced-motion gate** invariant below for exactly how that's gated — it is not simply "`useReducedMotion()` returns motion-off".
  This also removes a correctness bug the two-markup approach would have had: `useChapterProgress(ref)` takes a single `ref`, and assigning that same ref to two different DOM elements would silently point it at whichever one rendered last. This rule applies to all seven chapters and to the chrome. Projects (03) — absolutely-positioned overlapping panels on desktop vs. stacked cards on mobile — looks like it could strain a single-markup approach; **verify this when building that chapter, don't assume it holds; flag it there, not here.**
- **Mandatory invariant — mount/reduced-motion gate, and its exact polarity.** `useReducedMotion()` from `motion/react` (re-exported from its underlying `framer-motion` implementation — confirmed by reading the installed package: `motion`'s `dist/cjs/react.js` does `require('framer-motion')` and re-exports it wholesale, `motion` is a thin wrapper, not a rewrite) returns **`true` when the user prefers reduced motion** — i.e. `false` means motion is allowed. Getting this backwards silently inverts the entire fallback: treating `false` as "motion off" would run every scroll-driven effect for everyone by default and only disable them for the (rare) reduced-motion users' inverse case — the opposite of the intended default-safe behavior.
  Separately, this hook is **not safe to read directly on first render** for deciding what to draw: reading the installed source (`framer-motion.dev.js`, `initPrefersReducedMotion`/`useReducedMotion`), the browser's actual `matchMedia` value is read **synchronously inside the hook's own function body** the first time it's called — not deferred to a `useEffect` — so on the client's very first (hydration) render it can already return the real device preference, which was unknown during SSR (`null` server-side). If that device preference is `true`, the hydration render would try to produce different output than the server-rendered HTML, i.e. a mismatch/flash — the exact thing this gate is supposed to prevent.
  The correct pattern: keep a separate `mounted` boolean, `false` on the server and on the very first client render, flipped to `true` inside a `useEffect` (which only runs post-hydration). Scroll-driven effects (image transform, hint fade, word-reveal, chrome color-switching, Hero CTA fade-in) are active only when `mounted && !reduceMotion && isDesktop` — all three, not `!reduceMotion` alone. Until `mounted` flips, render exactly the static-state values (full-lit paragraph, hidden hint, etc.), which is also what SSR emitted — so there is never a mismatch, regardless of the visitor's actual OS preference.
