## Architecture, rules and constraints

- Builds on unit 09 Pass A (`app/[locale]/project/[slug]/page.tsx`, `generateStaticParams`, `getProjectBySlug`, `notFound()`, `evaluate()`-based MDX compilation) and unit 09b (header/intro/`Callout`, `components/mdx/callout.tsx`, the `text-center` MDX wrapper, `not-prose`/`clear-both` float pattern). No changes to Pass A's routing/data mechanics.
- **Content model decision (confirmed with user)**: unlike top1's header/hero-image (frontmatter-driven), all of this unit's content is authored directly inside the case study's `.mdx` body, appended after top1's `<Callout>` block:
  - The dashboard gallery and the flow diagram are custom MDX components (same pattern as `Callout`/`CalloutItem`) — **not** new `ProjectMeta` frontmatter fields.
  - The "10 steps happy path" list is a plain MDX ordered list (`<ol>` via standard Markdown numbering), styled by the existing `prose` defaults — no custom list component.
- **New components, both in `components/mdx/dashboard-gallery.tsx`**:
  - `DashboardGallery` — props `clientPcSrc: string`, `clientPcAlt: string`, `adminMobileSrc: string`, `adminMobileAlt: string`, `operatorPcSrc: string`, `operatorPcAlt: string`, `caption: string`. Renders the 3-box collage described in Design, plus one shared caption below it. `not-prose`. None of the 3 images render a per-image caption/label (confirmed with user) — the mockup's "dashboard cliente pc" / "dashboard admin mobile" / "dashboard operatore pc" strings are annotations identifying which screenshot goes in which slot, not real UI copy; a single `caption` covers all three (see the Revision note and Design below). Each image still needs a real `alt` string for accessibility, authored per-instance as an MDX component prop (not derived from the mockup labels verbatim — write a real descriptive alt text).
  - `FlowDiagram` — props `src: string`, `alt: string`, `caption: string`. Renders the full-width image + visible caption described in Design. `not-prose`, full width in normal block flow (no longer needs `clear-both` — see Revision note, the gallery no longer floats).
- **Revision (2026-08-09), per user follow-up after seeing the first implementation rendered in the browser**: the original float-based layout (gallery floated left, steps list flowing around it as MDX text) is replaced with an explicit two-column **flex** layout, because the user asked for exact width proportions and full-width coverage that a float can't reliably guarantee:
  - The gallery column and the steps-list column are wrapped together in one shared flex container, authored directly in the `.mdx` body (raw JSX, same technique already used for the steps' `text-left` div): `<div className="not-prose ... flex flex-col lg:flex-row ..."><DashboardGallery .../><div className="lg:w-[60%] text-left">...steps markdown...</div></div>`. `DashboardGallery` itself becomes the flex row's first child, sized `lg:w-[40%]` (was previously float-left with an emergent, content-driven width) — this single change is also what satisfies the user's "make it ~50% bigger" request: moving from a narrow, content-driven float column to an explicit 40%-of-full-page-width column makes the images substantially larger on its own, without a separate multiplier (flagged here explicitly rather than inventing a hidden number — confirm if an *additional* size increase was actually wanted on top of this).
  - **Row 1 (Client PC + Admin mobile) sizing — revised**: previously specified as a shared fixed height (both boxes forced to the same height, widths derived from that height + each box's own aspect ratio). Per explicit user decision, replaced with a **simple round-number width split** (Client PC wider, Admin mobile narrower) within the gallery column, each box's own `aspect-ratio` then determining its own height independently — the two boxes will end up at visibly different heights (confirmed acceptable by the user, trading exact mockup fidelity on this one point for simplicity).
  - **Mobile fill-width fix**: the previous implementation's row-1/row-2 boxes used a fixed `h-[clamp(...)]` height (in `rem`/`vw`), which produced small boxes squeezed to the left on narrow (mobile) viewports since the container had no width driving them wider. Switching to percentage widths (relative to the gallery column, which itself is `w-full` under `lg` and `lg:w-[40%]` at `lg`+) fixes this automatically — the same box-sizing rule now yields full-width boxes on mobile and a 40%-column set of boxes on desktop, with no separate mobile-specific values needed.
  - **Caption**: previously no caption was planned for the gallery. Per user request, one shared caption (not per-image) now renders below the 3 boxes, inside the gallery's own 40% column (not spanning the full row) — small, centered text, same treatment as `FlowDiagram`'s caption.
- **Second revision (2026-08-09), after the flex-layout rework was reviewed with real content**: two further changes, both confirmed with the user:
  - **Steps content is now real** (not placeholder) — the user provided the actual 10-step "happy path" flow for `remote-nif` in Italian; the assistant translated it to English (a translation of user-provided text, not invented content, same treatment as `summary`'s translation in top1). Both `content/projects/{en,it}/remote-nif.mdx` updated in place.
  - **Numbered-list styling, new component `components/mdx/steps-list.tsx`**: the plain-MDX-`<ol>` approach from the first revision is replaced with `StepsList`/`Step` (same props pattern as `Callout`/`CalloutItem` — `Step` takes a `label` string and `children` as the description). Two real problems drove this, found only once real content was reviewed in the browser: (1) the numbered markers were invisible — the steps list sits inside the page's `not-prose` scope (needed for the flex layout), which strips the default `<ol>` marker along with the rest of prose's typographic styling, so plain Markdown numbering silently disappeared; (2) the user asked for a specific two-color split within each item — the number and the label before the colon in bold `--color-heading` (black), the rest of the sentence in regular `--color-body` (dark grey), both existing design tokens already used sitewide (not new colors) — which plain Markdown cannot express (no way to color only part of a line without a component). `StepsList` renders an `<ol className="list-decimal list-inside marker:font-bold marker:text-heading">` (Tailwind's `marker:` variant colors just the number), `Step` wraps its `label` in a bold `text-heading` span followed by the description in `text-body`. This is a deviation from the original Architecture's "no custom list component" decision — recorded here rather than silently applied.
  - **Height balance between the gallery and the steps column, explicitly accepted as-is**: with the real (longer) step descriptions, the steps column runs noticeably taller than the 3-box gallery (the gallery ends roughly a third of the way down the steps list). The user was shown this in the browser and explicitly chose not to rebalance it (no further size increase, no restructuring to keep the gallery pinned alongside only part of the list) — the mismatch is accepted, not a bug to fix later.
- **Third revision (2026-08-09), simplification requested by the user after questioning why a custom component was needed at all**: the `steps-list.tsx` component from the second revision is **removed** — the user asked, correctly, whether plain Markdown (`1. **Label**: text...`) could have achieved the same result, and it turned out most of what drove the component was self-inflicted, not a hard Markdown limitation:
  - **Root cause**: `not-prose` had been applied to the *outer* flex wrapper (holding both `DashboardGallery` and the steps column), and `.not-prose` cancels prose styling for its entire subtree — including the steps column, which never actually needed it (only `DashboardGallery` does, because `next/image` renders a real `<img>`, which `.prose` does style). Removing `not-prose` from the outer wrapper (kept only on `DashboardGallery` itself, where it already lived) restores native `.prose` behavior — including working `<ol>` numbering — for the steps column.
  - **Two-color styling now done via Tailwind Typography's element modifiers** on the page's ancestor `.prose` div (`app/[locale]/project/[slug]/page.tsx`), instead of a component: `prose-strong:text-heading` (labels, written as plain Markdown `**bold**`) and `prose-li:text-body` (the rest of each item's text). Verified against the installed `@tailwindcss/typography@0.5.20` (`node_modules/@tailwindcss/typography/README.md`'s "Element modifiers" table) that `prose-strong:`/`prose-li:` are real, current modifiers targeting `strong`/`li` — not assumed from an older version.
  - **One real gap plain Markdown + modifiers couldn't close**: the `<ol>` marker's `font-weight` is hardcoded to `400` in the installed plugin's own source (`node_modules/@tailwindcss/typography/src/styles.js`, `'ol > li::marker': { fontWeight: '400', color: 'var(--tw-prose-counters)' }`) — there is no `prose-counters:`/`prose-marker:` modifier in the plugin's own documented list to override it. Fixed with a scoped arbitrary-variant utility on the same ancestor `.prose` div: `[&_ol>li::marker]:font-bold [&_ol>li::marker]:text-heading`. Confirmed safe to override (not fragile/`!important`-dependent) by checking the plugin's own generated selectors (`node_modules/@tailwindcss/typography/src/index.test.js`): every prose base style is wrapped in `:where(...)`, which has zero specificity, so a normal-specificity Tailwind utility targeting the same `::marker` wins cleanly.
  - Net result: `content/projects/{en,it}/remote-nif.mdx`'s steps are back to a plain Markdown `<ol>` (`1. **Label**: description`), `components/mdx/steps-list.tsx` deleted, `page.tsx`'s `StepsList`/`Step` import and MDX `components` map entries removed. All styling for this block now lives in one place (the ancestor `.prose` div's className in `page.tsx`), not spread across a dedicated component.
  - **Lesson, worth remembering for later microfasi**: applying `not-prose` defensively "to be safe" (as was done here, copying `Callout`'s precedent without checking whether the *whole* wrapper needed it) can silently disable native Markdown behavior (list markers, `<strong>` styling) for content that was never the reason `not-prose` was added — scope `not-prose` to the specific element that actually needs it (e.g. one containing a raw `<img>` or requiring custom non-typographic layout), not to a shared ancestor that also happens to wrap ordinary prose content.
- **Text alignment**: top1's MDX wrapper in `page.tsx` applies `text-center` to the entire compiled MDX output (`<div className="prose max-w-none text-center">`). The steps column overrides this locally with its own `text-left` class (on the `<div className="w-full lg:w-[60%] text-left">` wrapping the heading + list in the `.mdx` body) — a plain Tailwind override, unrelated to the `not-prose` question above (text-align inheritance is independent of prose/not-prose scoping). **Verified** (official MDX docs' "Interleaving" section + an empirical `compile()` test against the installed `@mdx-js/mdx@3.1.1`): Markdown content just needs to be on its own line, not on the same line as a JSX tag, for MDX to parse it as a block — blank lines are not required.
- **Real content vs. placeholder (confirmed with user)**: everything in this unit is placeholder for now — same treatment as top1's `Callout` copy and `coverImage`. Placeholder image paths follow the existing convention (`/images/projects/remote-nif/...`), rendered on `bg-muted` fallback via `next/image`, `object-contain` (per the user's global default preference, already corrected once in top1 — do not repeat the `object-cover` mistake). Placeholder path names, exact `alt` text, the steps heading text, and the 10 step strings (EN/IT) are written now as real placeholder content (not left as TODO markers) — logged as a non-blocking open question for real-copy replacement later, same treatment as `Callout`'s items in top1.
- **Collage arrangement (confirmed with user)**: staggered, non-overlapping boxes — faithful to `top2.png`, not the overlapping-blocks pattern used by Hero's collage (unit 04). No absolute positioning or negative offsets needed.
- No new `ProjectMeta` fields, no changes to `types/project.ts`, `lib/content.ts`, or Pass A's routing/`notFound()` logic.

## Design

Per `public/images/top2.png`. The mockup is mid-fi and its proportions are a **direction, not a pixel-exact target** — box shapes/relative sizes below are read from the mockup's approximate proportions, not measured to the pixel; adjust visually once rendered rather than treating these as exact.

1. **Outer two-column row** (shared flex container wrapping the gallery and the steps list, authored in the `.mdx` body): `not-prose flex flex-col lg:flex-row lg:items-start gap-[clamp(1.5rem,3vw,2.5rem)] mt-[clamp(2.5rem,5vw,4rem)]` — the top margin is the same rhythm value used for every other major vertical gap on this page (`Callout`'s own top margin in top1, `FlowDiagram`'s top margin below). Below `lg`: stacks (gallery column first, full width; steps column below it, full width). At `lg`+: side by side, gallery column fixed at `lg:w-[40%]`, steps column fixed at `lg:w-[60%]` — together spanning the full row width (confirmed with user: 40% image / 60% text, filling the entire container width, no leftover gap).

2. **Dashboard gallery** (`DashboardGallery`, the row's first flex child, `w-full lg:w-[40%]`):
   - **Row 1 — Client PC + Admin mobile**: a flex row, `gap-[clamp(0.75rem,1.5vw,1.25rem)]`. Widths are simple round percentages of the gallery column (not a shared height — see the Revision note in Architecture): **Client PC** `w-[62%]`, **Admin mobile** `w-[30%]` (the remaining ~8% is gap/breathing room). Each box's height is whatever its own `aspect-ratio` produces at that width — the two boxes will not be exactly the same height, which is an accepted, confirmed trade-off.
     - **Client PC** box: `aspect-[4/3]` (landscape/PC-shaped), `rounded-[20px]` (same explicit-radius reasoning as top1's hero image — a rectangular screenshot box, not the sitewide pill), `bg-muted` fallback, `next/image` `fill object-contain`.
     - **Admin mobile** box: `aspect-[9/19]` (narrow portrait/phone-shaped, similar spirit to Hero's mobile collage slot, unit 04 — this is the "shaped like a phone" box the user asked to confirm; already portrait before this revision and unchanged by it), same box treatment as above.
   - **Row 2 — Operator PC**: `mt-[clamp(1rem,2vw,1.5rem)]` above it, indented from the gallery column's left edge by `ml-[10%]` (approximate, matches the mockup's "not flush-left, not overlapping Admin mobile" direction — adjust visually once rendered). Width `w-[62%]` (matches Client PC's width, per the mockup — both PC-shaped boxes read as the same width), `aspect-[2/1]` (landscape, flatter/shorter than Client PC), same box treatment (`rounded-[20px]`, `bg-muted`, `next/image` `fill object-contain`).
   - No box overlaps another.
   - **Caption**: one shared caption below all 3 boxes (`mt-[clamp(1rem,2vw,1.5rem)]`), centered, `text-sm text-body` — same caption treatment as `FlowDiagram`'s and top1's hero-image caption. Covers all three images collectively (confirmed with user) — no per-image caption/label anywhere in the gallery.

3. **Happy path steps** (plain MDX content, the row's second flex child, `w-full lg:w-[60%] text-left`): a short heading directly above the list (e.g. "10 steps happy path" / translated for `it`, exact wording is the assistant's placeholder — confirm or change), then a plain numbered list (`<ol>`) with 10 short placeholder step strings. Left-aligned (see Architecture's text-alignment note) — this deviates from top1's center-aligned paragraphs, deliberately, to match the mockup's left-aligned numbered list. Default `prose` typography, no custom styling.

4. **Flow diagram** (`FlowDiagram`, `not-prose`, full width relative to the page's standard container, `mt-[clamp(2.5rem,5vw,4rem)]` — same vertical rhythm value as `Callout`'s top margin in top1; no longer needs to clear a float since the gallery above it is no longer floated, it simply follows in normal block flow after the two-column row closes): single full-width image, `bg-muted` fallback, `next/image` `fill object-contain`, `rounded-[24px]` (same non-pill treatment as `Callout`'s box, for the same reason — a large rectangular content block). Aspect ratio: the mockup's flow-diagram box is cropped at the bottom of the reference image, so its true proportions can't be read precisely — use an approximate wide/banner shape (`aspect-[16/7]`) as a placeholder ratio, explicitly flagged to revisit once a real diagram asset exists (same treatment as top1's `aspect-[19/10]` hero image estimate). Below the image: a visible caption (centered, `text-sm text-body`), placeholder text for now.

5. No responsive breakpoint tuning beyond the single structural switch already named above (two-column at `lg`, stacked below it) — consistent with every other section's structural-breakpoint-only rule (`ui_context.md`). On mobile, both dashboard-gallery rows now naturally fill the full mobile width (percentage-based sizing relative to a `w-full` column), rather than being squeezed to a small area on one side as in the first implementation.
